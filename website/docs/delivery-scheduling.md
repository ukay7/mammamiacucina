# Delivery date and time

Customer checkout and Quick Sale / New Order show separate delivery date and time fields. The initial selection is two elapsed hours ahead in America/Toronto, including date rollover and daylight-saving changes. Users can change the selection; two hours is the default, not a minimum lead time. Past dates/times and incomplete selections are rejected. Pickup hides and disables both fields and stores no delivery schedule.

`orders.delivery_scheduled_at` stores the selected instant in UTC. The migration adds a nullable column without assigning dates to existing orders. New invoices capture the schedule in their issuance snapshot. Order details, customer confirmations, POS order pages, packing slips, shared financial print/PDF documents, and order email snapshots display the selected instant in Toronto time with EST/EDT. Existing archived documents and invoice snapshots are not rewritten.

The shared form refreshes an untouched default when admin opens checkout, and resets it for the next sale. Edits and validation-error values are preserved. Browser timezone settings do not affect Toronto input interpretation. A hidden reference preserves the exact default instant if it falls in the repeated autumn hour; manually selected ambiguous/nonexistent clock times receive a validation message. The visible date/time always takes precedence over a reference for a different selection.

Older already-open forms that omit both schedule fields receive the same two-hour default on submission. New forms require both fields; explicit blanks are rejected. Successful checkout/POS retries return the original order and schedule even after that date/time or quote has expired. Switching an existing order to pickup clears its delivery schedule.

Admin's existing order amendment form also includes delivery date and time. It prefills the saved Toronto selection and preserves it when reopening or switching fulfillment. Orders without a schedule show the two-hour default. Save Order Changes applies the selection under the existing order permissions, status/payment restrictions, and revision check; the amendment history records the old and new Toronto times with the admin and reason. A new selection must not be in the past, but leaving an existing past time unchanged is allowed when editing other details. Older edit forms that omit both fields preserve the existing value (including null). Issued invoice snapshots and archived emails remain unchanged; current order views and newly generated order documents show the revised schedule.

Deployment: run `php artisan migrate --force` before serving the updated forms. The local installation uses only `2026_11_12_150000_add_order_delivery_schedule.php`; no dependency or environment changes are required. Verify PHP GD remains enabled before running the email outbox. Scheduling tests cover both entry points, Toronto midnight/DST boundaries, custom selections, validation, pickup, retries, and invoice snapshots.
